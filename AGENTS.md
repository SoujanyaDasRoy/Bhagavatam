# AGENTS.md - how to work on Bhagavatam

For any coding agent (Antigravity, Claude Code, others). This file is the working agreement. `CLAUDE.md` describes the architecture, `DESIGN_SYSTEM.md` the visual rules, `docs/agent/RUNBOOKS.md` the step-by-step procedures. Read this file first, every session.

## 0. The five rules that matter most

1. **One agent at a time in this folder.** Before touching anything run `git status --short`. If files you did not change are modified, someone else is working: do not edit those files, do not revert them, and say so in your report. Two agents rewriting the same screen has already cost work here.
2. **Verify on the emulator, not just the compiler.** A change is not done until it is built, installed, opened on the emulator and looked at (screenshot), with the crash log checked. See section 3. Say plainly what you did not test.
3. **Never commit or push unless asked.** When asked: no `Co-Authored-By` lines, no "generated by" lines, the commit is authored by the user's existing git identity. Run `tools/agent/commit_check.sh` first.
4. **Book text stays out of git.** The Gita Press Sanskrit, Hindi, English, Bengali and Odia text, the databases built from it, page images, OCR output, PDFs, APKs and anything with a key (`.env`) must never be staged. They are listed in `.gitignore`; if you create a new folder of such material, add it to `.gitignore` in the same change.
5. **Do not type out the translation by hand.** Extraction is done by the automated tools in `content/_bengali` and `content/_odia`. Do not transcribe scripture pages yourself, page by page. If a tool needs a key you do not have, stop and tell the user.
6. **Order of authority: owner decisions, then the real words of the book, then code, then data and test files.** `docs/agent/DECISIONS.md` holds the owner's final answers. Where a test file, a data file or the code disagrees with a decision, fix the file or code. Where a matching rule is in question, test it on every word of the book (`content/_search/compare_rules.py`) and let the real words decide. Test files are generated from accepted code, never hand-guessed.

## 1. Working style

- Do the task that was asked. Do not widen scope. If you notice something else broken, note it at the end instead of fixing it silently.
- Ask before anything hard to undo: deleting folders, force-pushing, rewriting history, overwriting databases, publishing a release. Everything else: proceed without asking.
- Read the code you are about to change, and grep for every caller of anything you modify.
- Reuse what exists (design tokens, `tr()`, `readingFont()`, `SettingsGroup`, `MarkedText`). Match the surrounding code's style and comment density.
- Report honestly: what changed, what you verified and how, what you could not verify, what is left. Never say "done" for something you did not run.
- Plain words. No marketing language in code comments or UI text.

## 2. Project rules (from the owner)

**Text and typography**
- No em dashes or en dashes anywhere a person reads (UI strings, README, docs, book text). Use a spaced hyphen ` - `, a comma, or a danda. The book text is normalised at load by `tidyDashes` in `SampleData.kt`.
- Every new UI string needs all three app languages (English, Hindi, Bengali). Use `tr(ui, "English", "हिन्दी", "বাংলা")` from `data/Episodes.kt` or add to `data/Strings.kt` / `data/SettingsText.kt`.
- Wording: English app says "Chapter", Hindi "अध्याय", Bengali "অধ্যায়"; the book title is shown in the language's own script.
- Indic text: font size at least 15sp, line height about 1.8. Use `readingFont(lang)` for any text in a reading language so Bengali and Devanagari get the right font.

**Language model (do not break this)**
- *App language* (`state.uiLang`) is for menus, buttons, labels.
- *Reading language* (`state.readLang`) is the language of the book text, the audio and the **titles**. `state.titleLang` is the reading language, or the app language when reading Sanskrit. Chapter and Skandha titles always use `titleLang` and `readingFont(titleLang)`.
- In translation-only reading, the language chips in the reader pick the single language being read; with the shloka showing they toggle layers. The chip that is lit must match the page.

**UI**
- Touch targets at least 48dp where practical; contrast WCAG AA; respect the `Motion` tokens.
- Use the existing theme tokens (`Brand`, `LocalReaderColors`, `Radius`, `Motion`). Do not hard-code colours that exist as tokens.
- Check every UI change in at least: app language English and Hindi, one light and one dark theme, font scale 1.3. A screen that only works in English is not done.
- Settings: one page per area in `ui/screens/Settings*.kt`, built from `SettingsGroup` / `EntryGroup` (`SettingsKit.kt`). New option = state in `AppState` (persisted, reset in `resetSettings`) + a row + a string in three languages.

**Privacy and offline**
- Reading, listening and search work fully offline. Online features are optional, off-switchable in Settings, and send only the single word being looked up.
- Notes, highlights and bookmarks stay on the phone (`annotations.db`). Never upload them.

**Do not do**
- Do not build or wire in ad-free scraping of YouTube (InnerTube or similar). It breaks YouTube's terms. Only official embeds / links.
- Do not add an AI "generated with" credit to commits or the README.

## 4. Content and database

- `content/content.db` is the master database; `app/src/main/assets/content.db` must always be the same file. After changing one, copy it over the other and bump `versionCode` / `versionName` in `app/build.gradle.kts` so installs replace the bundled copy.
- Bengali import flow: `content/_bengali/bn_extract` (extract, assemble) -> `content/_build/promote_bengali.py` (only complete chapters) -> `content/_build/add_bengali.py <db> <version>`. Only chapters that pass the checks go into `content/bn/`.
- After any database change run the verifier idea from `docs/agent/RUNBOOKS.md` section "Check a language in the database": no stray `॥` markers, no Latin letters, no empty verses, every pointer target has text.
- Odia lives in `content/_odia` and `content/or` (Tesseract draft, every chapter `needs_review`). It is not in the app. Do not add it to the database or the app without the owner's go-ahead, and do not promote an Odia chapter without a verification step.

## 5. Git

1. `git status --short` first (rule 1).
2. Stage only what you changed, or everything if asked to "commit everything", then run `tools/agent/commit_check.sh`. It fails if book text, databases, APKs, PDFs, `.env` files or key-like strings are staged.
3. Commit message: a short subject, then a paragraph on what and why. No co-author or tool credits.
4. Push only when asked.

## 6. Known gotchas

- Writing Python with quotes or backslashes through a shell heredoc often corrupts it on Windows. Write the script to a file first, then run it.
- "File modified since read" errors: re-read the file, then edit.
- In `AppState.kt` a property's `private set` must stay directly under it. Inserting a new property between them breaks the build.
- `Modifier.clip(RoundedCornerShape)` around reading text shaves off the first and last letters and the verse number. Do not clip paragraphs; clip only boxes that have padding.
- If a build says `Failed to find target with hash string 'android-35'`: the Android SDK on this machine may only have a newer platform (check `...\Sdk\platforms`). Install the missing one with `sdkmanager "platforms;android-35"` or tell the owner. Do not change `compileSdk` just to get a build through without saying so.
- APK file names can carry a version (`Bhagavatam-v1.1.0-debug.apk`). `tools/agent/verify.sh` picks the newest one.
- **Disk space:** on 2026-10-09 the `C:` drive was 100% full; by 2026-10-10 about 120 GB was free. A full drive blocks the emulator and makes Gradle fail. Check `df -h /c` before big downloads or builds; never delete the owner's files to make room, ask.
- Web search and fetch tools can fail; use `curl` for primary sources.
- Compose text with several scripts needs the right `fontFamily` per run, or glyphs fall back and look wrong.

## 7. Dictionary work (English, Hindi, Bengali, Odia)

Plan: `docs/superpowers/plans/2026-10-09-dictionary-db.md`. Follow its tasks in order; do not start the Android tasks before the pipeline tasks (0 to 4) have produced real coverage numbers.
- **Licences first.** Only use sources marked `verified` in `content/_dict/sources.json`. Samsad Bangla and the Oxford McGregor dictionary are rejected (copyrighted). Task 0 is a gate: send the owner the list of sources and licences and wait. CC BY-SA sources require a credits screen with source, licence and link.
- **Never crawl the Wikimedia web API page by page.** It returns 429 within minutes and is against their guidance. Use the official dumps, a real User-Agent with a contact address, resume support and back-off.
- **Do not hand-type dictionary entries or scripture.** Entries come from the parsed sources only.
- **Generated data stays out of git:** `content/_dict/work/`, `dictionary.db` and `app/src/main/assets/dictionary.db` are in `.gitignore`. The scripts and `sources.json` are committed.
- **Size budget:** `dictionary.db` at most 30 MB on disk and 10 MB added to the APK. If you go over, tighten the filters; never drop a language and never go over silently.
- **Check every build:** `python tools/agent/dict_check.py <path-to-db> --max-mb 30` must print no FAIL. It cannot judge whether a meaning is right, so read the sample it prints.
- **Odia is incomplete** and its source text is an unverified Tesseract draft. Report Odia coverage as a number; do not claim it is complete; show the limit in the app.
- **A meaning is a dictionary sense, not a translation of the verse.** Word it that way in the UI.
- In the Android work reuse `OnlineMeaning` (move its suffix tables into `Lemmatizer`), `readingFont()`, `tr()` and the settings kit. Every string in three languages, no em dashes.

## 8. Search work

Plan: `docs/superpowers/plans/2026-10-09-search.md`. The objective target is `content/_search/gold_queries.json`; run `python content/_search/eval_queries.py` before and after every change to the search logic. No `required` query may fail. A `target` query that starts to pass must be promoted to `required` in the same change.
- **Do not use SQLite FTS5.** Android's SQLite at the minimum version (API 26, SQLite 3.18) cannot be relied on for it, and its default tokenizer breaks Indic words into single letters. The index is our own tables in `search.db` (plan section 3.2).
- **The English column spells names with diacritics** (Kṛṣṇa). Never search names by scanning columns with `LIKE`; use the index and the loose phonetic key.
- **The loose key must be identical in Python and Kotlin.** The shared test file `content/_search/tests/loose_pairs.json` is read by both tests. The pairs are generated from `prototype.py`, never hand-edited, and checked in Python by `py content/_search/tests/test_loose_pairs.py`. To change a rule: test it on the real words first (`compare_rules.py`, see `docs/agent/DECISIONS.md`), change the code, regenerate the pairs, run both tests, re-run the gold queries.
- **`search.db` is tied to a database version.** It records the `content_version` it was built from; the app must refuse a mismatching index. Rebuild it whenever `content.db` changes.
- **Related words and aliases must be verified against the book text** (the word must occur) before they go into `aliases.json`. Do not add synonyms from memory.
- **Generated data stays out of git:** `content/_search/work/`, `content/_search/search.db` and `app/src/main/assets/search.db` are in `.gitignore`.
- **Speed budget:** first results in under 50 ms on the emulator or phone, never on the main thread, stale queries cancelled. Size budget: `search.db` at most 8 MB (target 4 to 5 MB). Report real numbers in section 5 of the plan.
- **Shared code with the dictionary:** `Normalise.kt` and `Lemmatizer.kt` serve both plans. Check whether they exist before writing them, and do not make two copies.
- Odia text in the app is an unverified draft: build Odia search last and say so.
