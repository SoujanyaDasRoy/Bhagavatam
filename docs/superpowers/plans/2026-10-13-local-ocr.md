# Local Odia and Bengali OCR, extraction and accuracy repair: plan

**Goal:** an offline toolchain on the owner's PC that (1) reads the printed Gita Press pages in Odia and Bengali with a recogniser trained on this book's own typeface,
(2) extracts Odia for Skandha 6 to 12, (3) finds and fixes accuracy problems in the Odia and the Bengali texts, with every fix logged and measured. No cloud model, no API key.

**Status:** plan only, nothing built. Written 2026-10-13.

## 1. Facts this plan stands on (measured, not assumed)
| Fact | Source |
|---|---|
| The PC: Ryzen 5 5600H (6 cores), 15 GB RAM, RTX 3050 Laptop 4 GB VRAM, 120 GB free disk. PyTorch installed is the CPU build. Tesseract is not installed on PATH. | checked 2026-10-13 |
| Stock Tesseract (`ori`) is wrong on 25% of words on this book (page median 24%, worst 80%). Systematic confusions: `ୟ`/`ଯ`, `ି`/`ୁ`, `ଙ`/`ର`, `ୱ`/`ଵ`, `ଚା`/`ଗ୍ବ`. | `docs/agent/ODIA_ACCURACY.md` |
| 491 Odia pages (Skandha 1 to 4) have a transcript already. It was made by a vision model and is **not human-audited**: it is an answer key of unknown purity. | `content/_odia/vision_transcripts` |
| Bengali: about 13,400 verses have text; known defects: 232 verses without text, 129 unmatched blocks, 799 stray `॥` rows, 21 rows with Latin letters in the shipped database. | `content.db` meta, earlier review |
| One printed typeface and layout for the whole edition. This is the case where a recogniser trained on the book itself beats general engines by a wide margin. | print inspection (page 579) |
| Odia and Bengali already map onto Devanagari by block offset in `prototype.loose_from_indic`, so a verse's names can be compared across Hindi, Bengali and Odia. | `content/_search/prototype.py` |

## 2. Approach, and what is not promised
"A program that recognises Odia and Bengali" from nothing is not a sensible target; **fine-tuning an existing line recogniser on this book's own pages is.**
- Engine A: **Tesseract 5 LSTM fine-tune** (`lstmtraining --continue_from ori` and `ben`). CPU only, no GPU needed, the toolchain the pipeline already knows.
- Engine B (only if A misses its gate): a small **CRNN + CTC** model in PyTorch on the RTX 3050 (4 GB is enough for line images).
- A second, independent reading comes from a different engine or a different image preprocessing of the same engine, compared by the existing `odia_verify.py`.
- **Not promised:** a number. The expected gain is large for a single-typeface book, but the first real number comes from phase 2 on held-out pages. If the gate fails, the plan says what to do, not to lower the bar.

## 3. Phases, each with a gate
**P0. Environment and baseline (about half a day)**
- Install Tesseract 5 with `tessdata_best` `ori` and `ben` and check the training tools exist (`lstmtraining`, `combine_tessdata`); install CUDA PyTorch only if engine B is needed.
- Build `local_ocr/benchmark.py`: given an engine and a page list, compute word and character error against the trusted pages with `odia_text.wer`.
- Audit 300 random words of the Skandha 1 to 4 transcript with the existing `odia_review.py audit` first. **Gate:** error of the answer key at most 1%; if worse, fix the key (or train on Skandha 2 to 4 only) before anything is trained on it.
- **Result (2026-10-13, by Claude reading the page images; the owner cannot read Odia): GATE FAILED.** 23 random words judged before the audit was stopped: 2 wrong (8.7%, 95% interval 2.4% to 26.8%), so the 1% bound is already out of reach. Both errors are of a kind that automatic checks can find: `ଅଳଙ୍କାର` for printed `ଅଲଙ୍କାର` (la/retroflex la), and the nonsense conjunct `ଆଗ୍ର୍ୟ୍ୟ` for `ଆଚାର୍ଯ୍ୟ` (the print's `ଚା` looks like `ଗ୍ର`, the same confusion Tesseract has).
- **Consequence:** the transcript is not used as training truth as it stands. P1 gains a cleaning step: keep only lines where the transcript and an independent reading (stock Tesseract on the same line) agree to at least 0.9 character similarity, add a conjunct-validity filter (no `୍ୟ୍ୟ`, no virama chains that Odia never has, built from the lexicon), then bootstrap: train, re-read all lines, add the lines where the new model agrees with the transcript, repeat. The held-out Skandha 4 audit at the end is done against the page, not against the transcript.
- Output: baseline numbers for stock `ori` and `ben` on 20 pages each.

**P1. Line dataset from the book itself (about 1 day)**
- Reuse the layout code in `odia_ocr.py` (column rule, zones) and cut each translation column into line images (horizontal projection, as `vtools.cut_points` does).
- Align the answer-key text to lines: run stock Tesseract per line, then match each key paragraph to the lines by fuzzy sequence alignment (the key has paragraphs, not lines). Keep only lines whose match is above a threshold; throw the rest away rather than train on a wrong label.
- Split by chapter, never by page: train on Skandha 1 to 3, validation Skandha 4 (held out), no leakage.
- **Gate:** at least 15,000 clean line pairs; a hand look at 50 random pairs shows no mislabelled line.

**P2. Train and measure the Odia recogniser (about 1 to 2 days, mostly waiting)**
- Fine-tune Tesseract (`ori` base) on the training lines, evaluate on the held-out lines and on full pages of Skandha 4.
- **Gate:** word error on held-out Skandha 4 pages at most 4% (stock is 25%). If missed: add augmentation (blur, skew, scan noise), more lines, then engine B. Report the number whatever it is.

**P3. Extract Skandha 6 to 12 locally (about 1 day of compute)**
- `local_ocr/read_pages.py` writes the same page JSON as `odia_vision.py` (paragraphs, verse numbers, running head, chapter heading, colophon, footnotes), so `odia_verify.py`, `odia_review.py`, `odia_finalize.py` and `odia_assemble.py` run unchanged.
- Two readings: the fine-tuned engine at two scales or binarisations (or engine A and engine B). Skandha 6 first (110 pages) as the pilot; stop and show numbers.
- **Gate:** disputes under 5% of words on the pilot; structure check (verse numbers against the Hindi verse list) clean or explained.

**P4. Local accuracy repair, Odia and Bengali (about 2 days)**
New `local_ocr/repair.py`. Every automatic fix is logged to `repair_log.csv` (page, old, new, reason, score) and can be undone; nothing is rewritten silently.
1. **Impossible spellings** (existing `odia_text.severe`, plus a Bengali equivalent: Latin letters, Devanagari or Odia letters, stray marks).
2. **Confusion-aware dictionary fix:** a word that is not in the lexicon but is one known confusion pair (from the P0 table) away from exactly one lexicon word, and the character n-gram model prefers it, gets fixed. The lexicon is the trusted Odia text, the Odia Wiktionary entries and, for Bengali, the Bengali book text and Bengali Wiktionary.
3. **Cross-language name check:** for every verse, proper nouns in the Odia (or Bengali) translation must match, by the loose key, a word in the verse's Sanskrit, Hindi or Bengali text; a near miss (key distance 1) is flagged or fixed to the matching word's spelling. Measured first on Skandha 1 to 4 for precision before it is allowed to fix anything.
4. **Structure:** verse numbers in order against `expected_verses.json`, running-head chapter, colophon, duplicate or missing units.
5. **Bengali specifics:** run 1 to 4 on `content/bn`; the known defects above become a worklist; pages that stay suspicious are re-read with the fine-tuned Bengali recogniser (the same P1/P2 recipe on Bengali pages, train on Part 1, test on Part 2).
- **Gate (precision before reach):** on stock-Tesseract output of Skandha 4 with the answer key as truth, an automatic fix is right at least 98% of the time. Fixes below that go to the review list, not to the text.

**P5. Human audit and acceptance (about 1 day of the owner's time)**
- The existing `audit-sample` / `odia_review.py audit` / `audit-score`: 600 accepted Odia words, 300 Bengali words. Accept when the 95% upper bound on the error rate is at most 1%.
- Assemble with `odia_assemble.py --starts data/starts_s5_12.json`; verse-gap report must be clean.

**P6. Ship (about half a day)**
- Both `content.db` copies change together (CLAUDE.md invariant 5); `verification_status` follows the audit; a report with numbers only (no book text); commit code and docs, never data.

## 4. Files (new, under `content/_localocr/`, none containing book text)
`benchmark.py`, `make_lines.py`, `train_tesseract.ps1`, `read_pages.py`, `repair.py`, `confusions.json`, `tests/`; docs in `docs/agent/LOCAL_OCR.md`. Outputs, models and line images live in an ignored `work/` folder (they derive from the printed book).

## 5. Risks and what is done about them
| Risk | Plan |
|---|---|
| The answer key has errors and the model learns them | P0 audit gate; a held-out audit at the end measures against the page, not against the key |
| Line alignment mislabels lines | keep only high-confidence matches, a hand check of 50, train on fewer clean lines rather than more noisy ones |
| Tesseract fine-tuning on Windows is fiddly | engine B (CRNN/CTC on the GPU) is the planned fallback, decided by the P2 gate |
| CPU-only training is slow | training runs unattended overnight; only a few hundred thousand line-iterations are needed to fit one typeface |
| Skandha 10 commentary layout (full-width) | handled as its own layout case in `make_lines.py`; tested on its own pages |
| Automatic fixes that change correct text | precision gate, full log, undo, and the audit measures the final text, not the fixer |
| Copyright | all text and images stay in ignored folders; only code, numbers and docs are committed; use is the owner's private offline copy |

## 6. Order of work and cost
P0 to P2 decide whether the idea works and cost no money (compute only, a few days elapsed). P3 onwards is only started once the P2 number is on the table.
Hardware is enough for engine A and engine B. Nothing needs a cloud account.
