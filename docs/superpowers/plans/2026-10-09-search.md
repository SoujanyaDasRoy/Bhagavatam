# Search: research, features and implementation plan

> For the agent doing the work (Antigravity or any other): read `AGENTS.md` first (section 8 is about search), then this file. Work task by task in order. Each task has files, a test and an acceptance check. Tasks marked **GATE** need the owner's decision before you go on. The objective target is `content/_search/gold_queries.json`, run with `python content/_search/eval_queries.py`: no required query may fail.

**Goal:** a search box where a person types a name, a word or a reference in any script or in plain English spelling, and gets the right verses, chapters and stories at once, offline, ranked sensibly, with the matching words highlighted.

Works together with `2026-10-09-dictionary-db.md`: both use the same spelling normalisation and word-ending rules, built once (`Normalise.kt`, `Lemmatizer.kt`).

## 1. Research findings (measured on 2026-10-09)

### 1.1 How search works today
`SampleData.searchVerses` runs `LIKE '%query%'` on each language column (`en`, `hi`, `bn`, `sa`, `iast`), ORs them, and returns up to 100 verses in book order. `SearchFinder.find` then finds the match inside the text to cut a snippet. There is no index, no ranking, and no Odia. Stories (`Episodes.matchesQuery`) are a separate substring test. A reference such as `10.29.1` jumps straight to a chapter.

Measured on the real data (14,580 verses):

| Query | Result today | Why |
|---|---|---|
| `Krishna` (English column) | **0 verses** | the English text spells the name with diacritics (Kṛṣṇa); only `Kṛṣṇa` finds the 1,499 verses |
| `krishna` in the IAST column | **0** | same reason |
| `Gajendra` (English) | **0** | same |
| `crocodile elephant`, `हाथी मगर`, `হাতি কুমির` | **0** each | the whole query is matched as one string, not as two words |
| a Bengali word spelled with the other vowel length | misses | the book writes কুমীর; people type কুমির |
| speed | about 30 ms per column on a desktop, so likely 150 to 300 ms per column on a phone, times 5 or 6 columns, on every keystroke | full scan, no index |

So the main problems are: **spelling and script** (a query in one spelling or script cannot find the same word in another), **multi-word queries**, **no ranking**, and **speed**.

### 1.2 Why not SQLite full-text search (FTS5)?
1. Its default tokenizer **breaks Indic words apart**: `श्रीकृष्ण` became the fragments `श`, `क`, `ष`, `ण` (tested). An option that fixes this (`categories`) exists only in newer SQLite.
2. Android's own SQLite is old: the app's minimum (API 26) ships **SQLite 3.18**; Google's table gives 3.22 for API 28, 3.28 for API 30, 3.32 for API 31 to 33, 3.42 for API 34, 3.44 for API 35. The trigram tokenizer needs 3.34 or newer.
3. Google documents FTS3 and FTS4 for Room, not FTS5, and does not say FTS5 is compiled into the platform SQLite; reports say it often is not.
Conclusion: **do not depend on FTS5.** Build our own word index in ordinary tables, which work on every Android version and give full control over how Indic text is split and normalised. (Bundling a newer SQLite is the alternative; it adds a second SQLite copy to the app and is only worth it if our own index proves too slow.)

### 1.3 Prototype of the planned approach (`content/_search/prototype.py`)
Two keys per word, built offline for every word of the book:
- **Native word index:** the word in its own language, lightly normalised (NFC, no zero-width joiners, lower case).
- **Loose phonetic key:** the word turned into a rough Roman sound form that is the same whatever script it came from: Bengali and Odia letters are mapped onto Devanagari (the scripts are parallel), consonants that sound alike are merged (aspirates, retroflex, sibilants, nasals, v/b/w, y/j), vowel lengths are merged, a trailing inherent *a* is dropped, and `ṛ` becomes `ri`. Roman input (plain English spelling or IAST) goes through the same function.

A first, coarser key that dropped all vowels was **too loose**: `Kunti` matched 1,527 verses and `rasa` 1,151, because it also matched unrelated words (`krsn` matched आकर्षण "attraction"; `nrd` matched निरोध). Keeping the vowels fixed that:

| Query | Verses | Words it matched |
|---|---|---|
| Krishna | 1,555 | Kṛṣṇa, কৃষ্ণ, कृष्ण, कृष्णः |
| Kunti | 46 (was 1,527) | Kuntī, কুন্তী, कुन्ती, কুন্তি |
| Rasa | 119 (was 1,151) | रस, রস, Rāsa, रास |
| Narada | 367 | Nārada, নারদ, नारद |
| Yudhishthira | 246 | Yudhiṣṭhira, যুধিষ্ঠির, युधिष्ठिर |
| Gajendra | 21 | গজেন্দ্র, गजेन्द्र, gajendrā |

All must-match pairs matched (Krishna to कृष्ण and কৃষ্ণ, Yudhishthira, Narada, Shri, Rishi); all must-not-match pairs stayed apart. One key then holds about two spellings of a word on average. The gold-query checker passes **26 of 26 required queries** on the prototype.

Estimated index size: about 1.2 million (word, verse) pairs for the loose key plus about 1.5 million for the native indexes. As delta-coded posting lists that is **about 4 to 5 MB**; as plain table rows about 24 MB. Use posting lists (see 3.2).

### 1.4 What the prototype does not solve (the work of this plan)
- **Related words:** the English text says *alligator* (46 verses), almost never *crocodile* (8), never both words with *elephant* in one verse; Hindi uses मगर and ग्राह. A search for "crocodile elephant" finds nothing. Needs related-word sets and matching at chapter level.
- **Typos:** `Krshna` and `Arjna` find nothing.
- **Name variants that differ beyond transliteration:** Narasimha finds 6 verses while Nṛsiṃha and नृसिंह find 22 and 26. Needs an alias list.
- **Stories vs. text:** the story "Rasa Lila" does not point at chapter 10.29 through the text search. Stories need explicit chapter links.
- **Ranking:** nothing ranks yet (exact word before variant, name in chapter title before body, etc).
- **Odia:** no Odia text is in the app yet; the schema must allow it.

### 1.5 Not to repeat
- Do not count on the English column for names: it uses diacritics.
- Do not search by scanning columns on the phone: use the index.

## 2. How search should work (the product)

**What a person can type**
1. A **reference**: `10.29.1`, `10.29`, `10 29 1` goes straight to the verse or chapter (already works; keep, and keep out-of-range numbers like `13.1.1` from jumping).
2. A **name or word in any script or in plain English spelling**: `krishna`, `कृष्ण`, `কৃষ্ণ`, `Yudhisthira` all give the same results; Roman, Devanagari, Bengali (and Odia later) meet.
3. **Several words**: every word must appear (any order). If nothing has all of them in one verse, show chapters that do ("these words appear in the same chapter").
4. **A phrase in quotes**: `"Lord said"` matches the words next to each other.
5. A **misspelling**: suggest "Did you mean ...?" from the book's own vocabulary.
6. A **topic**: `Gajendra`, `Dhruva`, `Rasa Lila` shows the story first, then its chapters, then verses.

**What comes back, in this order**
1. A reference jump row, if the query is one.
2. **Stories** that match (with the chapters they cover).
3. **Chapters** whose title matches.
4. **Verses**, ranked, each with the matching words highlighted in a short snippet, labelled with the language of the match.
5. **Dictionary entries** (once the dictionary exists), linked to the entry page.
6. Your own **notes and highlights** that match.

**Ranking (simple and explainable)**
1. Exact word in the query's own language beats a spelling variant, beats a cross-language match.
2. A match in a chapter title or story beats a match in a verse.
3. All query words in one verse beats words spread over a chapter.
4. Words close together beat words far apart.
5. Rarer words count for more than common ones (a word found in half the book adds little).
6. Ties: the reader's chosen reading language first, then book order.

**Feel:** results appear as you type (about 150 ms after the last key), the first 20 immediately and more as you scroll; nothing blocks the screen; an empty query shows recent searches and the stories, as today.

## 3. Design

### 3.1 Files
```
content/_search/                    pipeline and research (scripts committed; outputs NOT committed)
  prototype.py  eval_queries.py  gold_queries.json          (exist and work)
  aliases.json                      names with several spellings, related-word sets  (to write)
  build_index.py                    content.db + aliases + stories -> search.db
  work/  search.db                  outputs (.gitignore)
app/src/main/assets/search.db       shipped index (.gitignore; rebuilt by the pipeline)
app/src/main/java/com/bhagavatam/app/data/
  Normalise.kt  Lemmatizer.kt       shared with the dictionary plan (pure functions)
  LooseKey.kt                       the loose phonetic key, Kotlin port of the prototype (must give identical output)
  SearchIndex.kt                    opens search.db, runs queries, returns ranked results
  SearchQuery.kt                    parses the query: reference, words, quoted phrase
ui/screens/Search.kt                results UI (exists; reworked)
```

### 3.2 `search.db` schema (version 1)
```sql
meta(key, value)                                      -- search_version, built, content_version it was built from
term(id, form, kind)                                  -- kind: 'native' or 'loose'; form is the normalised word or the loose key
posting(term_id, lang, blob)                          -- blob: delta-coded varints of verse ids (sorted), one row per (term, language)
verse_meta(id, skandha, chapter, num, speaker)        -- id = verse.rowid in content.db
chapter_title(skandha, chapter, lang, title_norm)     -- for title matches
story(id, key, chapters)                              -- stories and the chapters they cover
alias(form, canonical)                                -- 'nrisimha' -> 'narasimha', 'alligator' -> 'crocodile' ...
vocab(form, lang, freq)                               -- for "did you mean" (typo suggestions)
-- indexes: term(kind, form)
```
Verse ids must equal `content.db` rowids and the index must record which `content_version` it was built from; the app refuses an index whose version does not match the database (otherwise results point at the wrong verses). `lang` is `en|hi|bn|or|sa|iast`.

### 3.3 Query path (app)
1. `SearchQuery.parse`: reference? then words and quoted phrases. Fewer than 2 characters: no search.
2. For each word: `Normalise` it, add its stems (`Lemmatizer`), its aliases, and its loose key (Roman or Indic).
3. Look up the posting lists; intersect across words (verses), fall back to chapters if the verse intersection is empty; check phrase adjacency from stored word positions if needed (phase 2: positions are stored only if the size budget allows).
4. Rank as in section 2; cut to the top 100; read the verse rows for the top 20 first.
5. Build snippets and highlight the matching words in the text with the *same* normalisation, so highlighting works for variants too.
6. Run off the main thread; cancel the previous query when a new key arrives.

### 3.4 Limits and honesty in the UI
- The loose key is a sound match, not a meaning match: it can occasionally match an unrelated word; ranking puts exact spellings first.
- Related words come from a hand-checked list (`aliases.json`) and, later, dictionary senses; it is not general synonym search. Say "related words" in the UI, not "meaning".

## 6. Risks
- **The loose key can match unrelated words** (about a fifth of keys hold three or more different words). Mitigation: ranking puts exact and native-language matches first; tests in Task 1; a gold query for each reported bad match.
- **Kotlin and Python keys drifting apart.** Mitigation: one shared pairs file tested on both sides.
- **Index out of date after a content change.** Mitigation: `content_version` check; the build script is part of the content release runbook.
- **Related words invented rather than checked.** Mitigation: every alias or related word is verified against the text (it must occur) and reviewed.
- **Odia text is not verified**, so Odia search quality is unknown; build the Odia part last and say so in the app.
- **Another agent editing the same folder.** Follow `AGENTS.md` rule 1.

## 7. Not in this plan
Searching meanings of verses with an AI model; spoken search quality (the mic button exists and is separate); a Sanskrit morphological analyser; searching inside the dictionary beyond what the dictionary plan builds.
